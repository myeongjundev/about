ExplainSOC — Security-AI Performance Claim Checker (ALEPH Assignment 13)

2026.09

RolePlanning · Front-end implementation · User observation · Validation · Deployment

Scope15 reading rules, conclusion card, paper lab, six user sessions, reproducible ZIP, GitHub Pages

StrengthSelf-regulation

SituationSecurity AI product brochures lead with numbers like ‘99% accuracy’ but rarely say which test produced them. In my Assignment 10 paper, the same XGBoost scored Macro F1 0.9979 on a randomly split test and 0.3871 on a test holding only attacks absent from training.

JudgmentI chose not to build scores, grades or pass marks that judge a number good or bad. Instead, the tool checks the test conditions behind a number first, then turns missing evidence into questions to ask the vendor.

ActionI wrote 15 reading rules that find missing test conditions in brochure sentences and score tables and turn them into vendor questions, and built a conclusion card and a paper lab for changing the paper's experiments directly. Rather than adding features, I recorded first-time users six times and fixed each place they got stuck. The app runs entirely in the browser, with no server.

ResultA fellow trainee reached the vendor questions on a phone unaided; 187 tests gate every deploy.

StackReact 19 · TypeScript · Vite 8 · Vitest · Playwright

Plan–Do–See Diary Account Authentication (ALEPH Assignment 7)

2026.09

RoleAuthentication design · Full-stack implementation · Validation · Deployment

ScopeArgon2id password storage, JWTs bound to server sessions with refresh-token rotation, per-account data isolation, migration of existing records, Docker deployment on Render

StrengthSelf-regulation

SituationI had to turn a Plan–Do–See diary that started as a public app into one based on personal accounts. A JWT checked only by its signature stays valid after logout until it expires, and hiding the diary behind a login screen alone would still leave a path to read other accounts' records.

JudgmentI bound each access JWT to a server session row so every request checks that the session is alive and who owns the data, and treated a reused, already-rotated refresh token as possible theft that revokes the whole token family.

ActionI stored passwords with Argon2id and limited lists, single records, statistics and exports to the user ID confirmed by the server. Existing records were backed up and moved to the new account, and changing the password revokes every existing session.

ResultPassed 319 back-end and 76 front-end tests, with request/response evidence that access to other accounts' data and reused tokens are rejected.

StackReact · TypeScript · Flask · PostgreSQL · Argon2id · Docker

AI Handoff Without Sharing the Conversation (ALEPH Assignment 5)

2026.08 - 2026.09

RoleExperiment design · Front-end implementation · Validation · Deployment

ScopeTen fixed checks, a slider that overlays the original and finished card, a seven-part handoff document, unit and E2E regression tests, GitHub Pages deployment

StrengthSelf-motivation

SituationEvery time I switched AI tools I had to explain the same context again, and it had never been tested whether the next AI could safely continue the same project without the conversation.

JudgmentInstead of racing for speed, I fixed the feature scope and ten fixed checks first, and tested whether the next AI could take over from code, checks and a handoff document alone, without the conversation.

ActionI first set the rule that a check not actually run is never recorded as passed, and had the first AI implement only checks 1–3 and stop as planned. The next AI read only the handoff document and finished checks 4–10 and the full regression suite. When the next AI read the first AI's work log before the prohibition rules, I did not hide that procedural violation behind the passing result; I left it in the work log and on the public page.

ResultPassed all 10 fixed checks; 85 unit and 38 E2E tests stayed green with no human code fixes.

Security Board with Alerts and Privilege Revocation (course lab)

2026.09

RoleSecurity feature design and implementation · Automation integration · Validation

ScopeRole-based access control with admin safeguards, an n8n sign-in alert bot with three messenger channels, porting the course's automatic over-privilege revocation code, Graylog SYN flood detection

StrengthSelf-regulation

SituationI had to add role-based access control to a board from class and port the course's code that automatically revokes excess privileges. If automatic revocation misfired, it could demote even the administrators and leave no one able to manage members.

JudgmentThe more automatic a revocation feature is, the more it must first prevent administrators from locking themselves out, so I applied the same rules that forbid self-demotion, self-deletion and demoting the last administrator to the revocation bot.

ActionI split the revocation bot into three stages (report only, notify Graylog, actually demote) so it removes privileges only when given the option, and kept evidence captures and alert senders from exposing API keys or webhook addresses on screen or in error messages. In the SYN flood lab I did not stop at seeing the alert arrive; I compared it with the run record and fixed a bug where the attack was marked as allowed and the real source and count were missing.

ResultPassed 45 tests; a 35,033-packet SYN flood from Kali reached Graylog, n8n, three messengers and the board log.

StackFlask · MySQL · JWT · n8n · Graylog · Docker
