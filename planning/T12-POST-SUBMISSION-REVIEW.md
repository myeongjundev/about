치명적인 누락이나 재현 실패는 발견하지 못했다. 이후 작업은 제출 오류 수정이 아니라 릴리스

## 잘된 점

### 1. 제출물이 하나의 기준으로 연결된다

`content/approved.json`을 중심으로 사이트와 문서가 만들어져 같은 사실을 서로 다르게 적을
가능성을 줄였다. 숫자·작업·경력 설명이 사이트와 문서에서 반복되더라도 원본은 한 곳이다.

### 2. 재현성을 말이 아니라 해시로 증명한다

기록 갱신 장치를 두 개의 새 임시 폴더에서 실행하고 결과 파일의 SHA-256을 비교한다. 제출 ZIP도
파일 순서와 시간을 고정해 같은 입력에서 같은 바이트가 생성된다.

### 3. 사실과 미확정 내용을 구분한다

AWS 환불 결과와 대학명처럼 확인하지 못한 내용은 넣지 않았다. 자동 검사 통과 여부와 실제로
수행하지 않은 검사를 구분하고, AI 인계 과정의 절차 위반도 결과가 좋다는 이유로 감추지 않았다.

### 4. AI와 본인의 판단 경계가 구체적이다

AI에게 맡긴 구현·검사와 본인이 결정한 공개 범위·작업 선택을 구분했다. 로그인 서비스 링크를
빼고 공개 저장소만 남긴 판단도 과제의 익명 접근 조건과 연결된다.

### 5. 채점자가 확인할 경로가 짧다

`submission/README-FIRST.md`와 `submission/CHECK-HOWTO.md`가 사이트, 문서, 장치 확인 순서를
짧게 안내한다. ZIP에서 실행되는 명령과 저장소에서만 실행되는 명령도 분리돼 있다.

## 이후 개선 항목

### P1 릴리스 생성 단계에 외부 URL 검사를 포함한다

현재 `device/validate_release.py --check-urls`는 외부 링크를 검사하지만,
`release/build_release.py`가 검증기를 호출할 때는 `--check-urls`를 붙이지 않는다. 링크가 깨진
상태에서도 ZIP 생성 자체는 성공할 수 있다.

개선안:

1. `build_release.py`가 기본적으로 `--check-urls`를 사용한다.
2. 네트워크 없는 환경을 위해 `--skip-url-check`를 명시적 예외 옵션으로 둔다.
3. 검사한 URL, 최종 응답 URL, 상태 코드를 릴리스 보고서에 기록한다.

### P1 최종 ZIP 전체를 대상으로 비밀값을 검사한다

현재 검사는 private key와 `api_key`, `secret`, `password` 형태를 중심으로 텍스트 파일을
살핀다. DOCX·PDF·이미지와 서비스별 토큰 형식은 자동 검사 범위가 좁다.

개선안:

- Discord·Slack Webhook, Telegram Bot Token, GitHub Token 형식 추가
- DOCX의 XML과 관계 파일을 풀어서 검사
- PDF 텍스트와 문서 메타데이터 검사
- ZIP을 생성한 뒤 다시 풀어 실제 제출 파일 전체를 검사
- 이메일·전화번호·내부 IP처럼 공개 범위를 확인해야 하는 값은 허용목록과 함께 검사

### P2 갱신 날짜를 빌드 결과와 동기화한다

최종 수정과 제출 기록은 2026-09-21인데 `README.md`의 최종 공개 빌드 날짜와
`content/approved.json`의 `updatedAt`은 2026-09-20이다. 채점에는 영향이 없지만 유지보수자가
어느 날짜를 믿어야 할지 혼동할 수 있다.

개선안:

- 사이트 또는 문서 내용이 바뀌면 `updatedAt` 갱신을 요구한다.
- Git diff가 있는데 날짜가 이전 값이면 검증 실패 처리한다.
- README의 상태 날짜는 승인 데이터에서 자동 생성한다.

### P2 T13 예정 자리 규칙을 한 문장으로 통일한다

`planning/REQUIREMENTS.md` 앞 표에는 “공개가 끝난 결과물만 두고 T13은 완료 후 추가”라고 적혀
있지만, 뒤의 최종 결정은 과제 원문에 따라 T13 예정 자리를 먼저 둔다. 실제 결과물은 뒤의 결정이
맞게 반영됐다.

개선안:

- 앞 표를 “완료된 결과물과 과제가 요구한 T13 예정 자리만 둔다”로 바꾼다.
- 이전 판단과 변경 이유는 `STATUS.md`에만 이력으로 남긴다.

### P2 경력기술서 마지막 쪽의 정보 밀도를 조정한다

경력기술서 4쪽에는 SOC SHIFT 항목 하나만 있어 여백이 크다. 항목을 쪼개지 않은 판단은 읽기
쉽지만, 채용용 문서로 계속 사용할 때는 3쪽 구성도 검토할 수 있다.

개선안:

- 항목 간 간격과 본문 행간을 소폭 조정해 3쪽으로 맞춘다.
- 4쪽을 유지한다면 기술 요약이나 검증 링크 모음을 추가해 쪽의 목적을 분명히 한다.
- 글자 크기를 줄여 억지로 압축하지 않는다.

### P3 공개 사이트를 채용자용과 과제 증적용으로 나눈다

사이트는 과제 요구를 충실히 보여 주지만 3분 안에 읽기에는 정보량이 많고, 대표작과 경력에서
같은 프로젝트가 반복된다.

개선안:

- 첫 화면에는 핵심 프로젝트 3개와 결과 수치만 남긴다.
- 상세 상황·판단·행동은 펼침 영역이나 개별 사례 페이지로 이동한다.
- 과제 제출용 설명은 보존하되, 채용자용 기본 화면에서는 결과와 본인 기여를 먼저 보여 준다.

### P3 팀 경험 문장의 어조를 다듬는다

“첫 모임에 두 명만 참석”, “비전공자 세 명”은 사실과 어려움을 설명하지만 독자에 따라 팀원에
대한 평가처럼 느낄 수 있다.

추후 채용용 표현에서는 “초기 참여 편차와 경험 배경 차이가 있었다”처럼 문제를 중립적으로
설명하고, 본인이 만든 프로토타입·이슈·리뷰 체계에 더 빨리 초점을 맞추는 편이 좋다.

## 권장 개선 순서

1. 릴리스 URL 검사와 최종 ZIP 비밀값 검사를 강화한다.
2. `updatedAt`과 README 상태 날짜를 현재 빌드와 맞춘다.
3. T13 예정 자리 요구사항 문장을 통일한다.
4. 경력기술서 4쪽의 여백과 사이트의 반복 내용을 채용자 관점에서 줄인다.
5. T13을 마치면 예정 카드를 실제 결과·링크·검증 수치로 교체한다.

## 최종 평가

제출본은 요구사항 충족, 익명 접근, 문서 품질, 반복 실행과 결과 재현 측면에서 안정적이다.
Claude가 요구사항 대조와 마무리를 꼼꼼하게 수행했고, 특히 판단을 바꾼 이유와 확인하지 못한
사실까지 기록한 점이 좋다.

다음 개선의 핵심은 기능을 더 붙이는 것이 아니다. 현재 강점인 정직한 증거와 재현성을 유지하면서,
릴리스 검사를 제출 파일 전체로 넓히고 채용자가 핵심을 더 빨리 읽게 만드는 것이다.
