## 1. 먼저 고정할 목표

T12의 결과는 단순한 포트폴리오 페이지가 아니다. 다음 네 결과물이 같은 사실과 같은 문장을
공유해야 한다.

1. 처음 온 사람이 3분 안에 읽을 수 있는 공개 자기소개 사이트
2. 사이트와 사실이 일치하는 이력서·자기소개서·경력기술서
3. 새 기록을 넣어 숫자와 문장 후보를 다시 만드는 재현 가능한 장치
4. URL·문서·장치·확인 방법·AI 판단 기록을 묶은 제출 패키지

성공 조건은 “예쁘다”가 아니라 아래 다섯 가지다.

- 이야기의 고난 → 회복 → 현재 흐름이 분명하다.
- 세 능력이 주장만이 아니라 날짜 있는 행동 장면으로 보인다.
- 모든 숫자는 출처와 기준일을 가진다.
- 같은 입력은 같은 결과를 만든다.
- 제출자가 직접 판단해야 하는 문장은 자동 생성하지 않는다.

## 2. 설계 전제와 중단 조건

현재 `planning/REQUIREMENTS.md`는 동기에게 받은 안내를 요약한 것이다. 따라서 실제 과제 화면의
원문을 받기 전까지는 **작업 기준안**이며 확정 규격이 아니다.

다음 두 항목은 구현을 시작할 수 없게 만드는 조건이 아니라, 최종 제출을 막는 조건이다.

- 본인 과제 화면의 T12 원문 또는 전체 캡처가 없음
- 학원 PC에서 받은 27일치 리추얼 JSON·출석 기록·제출 현황 원본이 없음

원문을 받기 전에는 구조·템플릿·샘플 데이터·검사기를 만들 수 있다. 실제 숫자와 최종 문구를
공개하고 제출하는 단계에서는 반드시 원문과 최신 입력을 다시 대조한다.

## 3. 핵심 설계 원칙

### 3.1 단일 사실 원본

사이트와 문서에 같은 문장을 복사해서 따로 고치지 않는다. 사람이 승인한 공개 정보는
`content/approved.json` 한 곳에 둔다.

```text
비공개 원본 기록 ──▶ 집계·후보 생성 ──▶ 사람이 확인·선택 ──▶ approved.json
                                                         ├─▶ 공개 사이트
                                                         ├─▶ 문서 3종 원고
                                                         └─▶ 제출 확인표
```

장치는 문장 후보를 제안할 수 있지만 다음 내용은 사람이 직접 작성하거나 승인한다.

- 첫 화면 한 줄 소개
- 이야기의 첫 문장과 마지막 문장
- 어떤 개인 정보를 공개할지
- 능력과 장면의 연결
- 최종 문서에 들어갈 표현

### 3.2 공개·비공개·제출 영역 분리

| 영역 | 포함 내용 | Git |
|---|---|---|
| 비공개 입력 | 리추얼 원본, 출석 원본, 제출 현황 원본 | 제외 |
| 승인 콘텐츠 | 공개하기로 정한 문장·숫자·연락 수단 | 포함 |
| 공개 사이트 | 정적 HTML/CSS와 공개 문서 | 포함 |
| 장치 소스 | 파서·빌더·반복 검사·합성 예시 | 포함 |
| 최종 제출 | 사이트 주소, 문서, 장치 ZIP, 제출문 | ZIP은 제외하고 로컬 생성 |

비공개 원본은 최종 ZIP에도 넣지 않는다. 장치 ZIP에는 합성 예시 입력과 실제 원본에서 만든
공개 집계 결과만 넣는다.

### 3.3 재현성과 단순성 우선

- 사이트: HTML·CSS 중심의 정적 페이지, 프레임워크 없음
- 장치: Python 3.12 표준 라이브러리만 사용
- 핵심 내용은 JavaScript가 꺼져도 모두 보임
- 출력 정렬, 날짜 형식, 개행, JSON 키 순서를 고정
- 실행 시각·절대경로·임시 폴더명을 결과에 기록하지 않음
- 외부 API와 생성형 AI가 없어도 새 폴더에서 실행 가능

## 5. 콘텐츠 설계

### 5.1 첫 화면

첫 화면에서 10초 안에 아래 내용이 보여야 한다.

- 이름: 김명준
- 역할: 신입 풀스택 개발자 또는 본인이 확정한 역할명
- 한 줄 소개: 반드시 “...한 사람”으로 끝나는 본인 작성 문장
- 바로 가기: 이야기 · 숫자 · 대표작 · 경력 · 문서
- 공개 연락 수단 하나

기술 목록은 도구 이름을 나열하는 대신 실제 프로젝트에서 사용한 것만 네 묶음으로 제한한다.

- Frontend
- Backend
- Data/AI
- Infra/Security

### 5.2 이야기

이야기는 아래 세 장면으로 고정한다. 기존 HTML의 오래된 순서를 사용하지 않는다.

| 단계 | 날짜 | 장면 | 능력 | 보여 줄 행동 |
|---|---|---|---|---|
| 고난 | 2024.12 | 대학 프로젝트 종료 뒤 남은 AWS 비용 수습 | 자기조절력 | 당황한 뒤 청구 내역 확인 → 리소스 삭제 → 지원 요청 자료 정리 |
| 다시 일어난 날 | 2026.06.26~08.04 | CLOV를 이슈와 리뷰로 끝까지 연결 | 대인관계력 | 프로토타입 제시 → 이슈·리뷰 흐름 마련 → 팀 작업 통합·배포 |
| 더 나아진 지금 | 2026.08.11~ | ALEPH에서 네트워크·보안을 다시 배움 | 자기동기력 | ping·로그·대역·설정 순으로 원인 확인 → T10 연구 완주 |

본문은 총 1,400~1,700자로 제한한다.

- 첫 문장: 본인 작성
- 장면별 요약 한 줄: 먼저 읽어도 전체 흐름이 이어짐
- 장면별 본문: 날짜·상황·행동·결과가 있음
- 마지막 문장: 본인 작성
- 다른 사람 이름, 대화 재구성, 확인되지 않은 감정·환불 결과는 넣지 않음

현재 `STORY-DRAFT.md`의 사실은 사용할 수 있지만, 다음은 다시 확인한다.

- AWS 금액을 공개해도 되는지
- CLOV 이슈·PR 숫자의 기준 시점
- ALEPH에서 가장 선명했던 실제 장애 해결 장면 하나
- “코리아AI 아카데미”와 “SKT ALEPH” 과정명·기간 표기의 정확한 명칭

### 5.3 숫자

숫자는 세 개만 사용한다. GitHub 커밋 수나 임의의 활동량은 넣지 않는다.

| ID | 표시 | 출처 | 연결 |
|---|---|---|---|
| attendance | 출석일 / 확정 수업일, 지각·결석 | 내 출석 기록 | 과정 지속성 |
| ritual | 아침 리추얼 작성 수업일 / 확정 수업일 | 내 리추얼 기록 | ALEPH 현재 장면 |
| submissions | 기한 안에 낸 과제 / 제출 대상 과제 | 내 제출 현황 | 대학 때 미완성과 현재 완주의 대비 |

모든 숫자는 `값`, `무엇을 셌는지`, `출처`, `기준일`, `분모의 정의`를 함께 표시한다.
최종 제출 현황이 확보되면 `submissions`를 고난 장면과 짝짓고, 그 전까지는 출석을 임시로
짝짓되 제출본에서는 “임시” 상태를 허용하지 않는다.

### 5.6 문서 3종

- 자기소개서: 사이트 이야기와 같은 사실을 사용하되 문서 읽기 흐름으로 재편집
- 경력기술서: 프로젝트마다 능력·상황·행동·결과·기술·기간·확인 링크

세 문서는 `approved.json`에서 DOCX로 생성한다. PDF는 보조본으로 만들 수 있지만, DOCX 제출
여부를 원문에서 확인한다. 사이트의 문서 링크는 실제 파일이 생기기 전에는 `<a>`가 아닌 준비
상태 텍스트로 둔다.

## 6. 승인 데이터 구조

`content/approved.json`은 공개해도 되는 값만 가진다. 비공개 원본의 문장 전체를 복사하지 않는다.

```json
{
  "profile": {
    "name": "김명준",
    "role": "",
    "tagline": "",
    "contact": {"label": "", "href": ""}
  },
  "story": {
    "firstSentence": "",
    "lastSentence": "",
    "segments": [
      {
        "id": "setback",
        "date": "2024-12-05",
        "stage": "고난",
        "ability": "자기조절력",
        "summary": "",
        "body": ""
      }
    ]
  },
  "numbers": [],
  "works": [],
  "experience": [],
  "documents": [],
  "updatedAt": "2026-09-19"
}
```

빈 문자열이나 `[TODO]`가 하나라도 있으면 `validate_release.py`가 실패해야 한다. 단, T13 앱의
`status: planned`는 허용하고 `plannedDate`는 필수로 검사한다.

## 7. 장치 설계

### 7.1 입력

- `ritual.json`: 날짜별 아침·마무리 기록
- `attendance.json`: 수업일, 출석, 지각, 결석
- `submissions.csv`: 과제 ID, 마감일, 제출일, 상태

실제 입력 형식은 원본을 받은 뒤 고정한다. 파서는 알 수 없는 필드를 무시하되 필수 필드가 없으면
조용히 0으로 처리하지 않고 명확한 오류를 낸다.

### 7.2 출력

`refresh.py`는 다음만 만든다.

- `numbers.json`: 집계값·출처·기준일·분모 정의
- `candidates.json`: 능력별 문장 후보, 날짜, 근거 ID
- `candidates.md`: 사람이 읽기 쉬운 후보 보고서

동료 이름·감사 대상·자유 입력의 연락처 패턴은 출력 전에 가린다. 후보는 자동으로 사이트에
들어가지 않는다.

### 7.3 반복 실행 검사

`check_repeat.py`는 새 임시 폴더 두 개에서 같은 합성 입력을 실행한다.

1. 출력 파일 목록 비교
2. 각 파일 SHA-256 비교
3. 기대 결과와 비교
4. `PASS` 또는 실패 원인 출력

절대경로와 실행 시각이 출력에 포함되지 않아야 한다. 종료 코드는 성공 0, 실패 1로 고정한다.

### 7.4 릴리스 검사

`validate_release.py`는 다음을 자동 검사한다.

- 사이트에 `.todo`, `[TODO]`, `[YYYY`, `준비 중` 오용이 없는지
- T13의 허용된 계획 상태 외 빈 필드가 없는지
- 문서 3개와 장치 README가 존재하는지
- 내부 링크와 파일 링크가 실제 대상을 가리키는지
- 허용되지 않은 로그인 필요 URL이 없는지
- 이메일·전화번호가 승인된 연락 수단 외에 나타나지 않는지
- 토큰·비밀번호·개인키 형태가 없는지
- 비공개 입력 경로가 ZIP 허용 목록에 없는지

외부 URL의 최종 검사는 인터넷 연결이 있을 때 별도 옵션으로 실행하고, 최종 제출 직전에
시크릿 창에서도 사람이 한 번 확인한다.

## 8. 공개 사이트 기술 설계

- `docs/`를 GitHub Pages의 `main /docs` 소스로 사용
- 상대 경로만 사용
- JavaScript 없이 핵심 콘텐츠 표시
- 모바일 320px 이상 지원
- 본문 최대 폭 약 680px
- 키보드 포커스 표시, 본문 바로 가기 링크, 의미 있는 링크 텍스트 제공
- `prefers-reduced-motion`에서 부드러운 스크롤 해제
- 문서 링크는 파일 형식과 크기를 함께 표시
- 외부 폰트가 실패해도 시스템 글꼴로 읽을 수 있게 구성

기존 D2의 색과 단순한 목록형 레이아웃은 유지할 수 있다. 왼쪽 영역을 실제로 고정할 필요는 없다.
내용을 끝까지 읽는 흐름이 우선이며, 모바일에서는 소개 → 바로 가기 → 이야기 → 숫자 → 대표작 →
경력 → 문서 → 연락 순서로 표시한다.

## 9. 제출 패키지

최종 제출 폴더는 허용 목록 방식으로 생성한다.

`README-FIRST.md`에는 공개 사이트 URL, 문서 위치, 장치 실행 명령, 확인 순서를 적는다.

`AI-JUDGMENT.md`는 다음 세 문장을 구체적으로 적는다.

1. AI에게 맡긴 일
2. 내가 직접 판단한 일
3. 따르지 않은 AI 제안과 이유

## 11. 구현 순서와 게이트

### Gate 0 — 원문과 입력 확보

- 실제 T12 원문 확보·요구사항 대조
- 27일치 이상 최신 리추얼 JSON 확보
- 출석 기록과 제출 현황 확보
- 마감일 확인

Gate 0을 기다리는 동안 템플릿·장치·검사기는 합성 입력으로 구현한다.

### Gate 1 — 본인 판단 확정

- 한 줄 소개
- 이야기 첫 문장·마지막 문장
- 이야기 세 장면 공개 범위
- 연락 수단 하나
- 학력·교육 공개 범위
- 세 번째 경력 항목
- T13 예정일

### Gate 2 — 사이트 최소 완성

- 승인 데이터 작성
- 이야기·숫자·대표작·경력 반영
- 모든 자리표시자 제거
- GitHub Pages 활성화

### Gate 3 — 문서 완성

- 같은 승인 데이터로 문서 원고 작성
- DOCX 3종 생성
- 렌더링 후 페이지 깨짐·문장 불일치 검수

### Gate 4 — 장치 완성

- 실제 입력 형식 파서 작성
- 합성 입력·기대 결과 작성
- 반복 실행 검사 PASS
- README대로 새 폴더 실행

### Gate 5 — 릴리스

- 허용 목록으로 ZIP 생성
- 자동 검사 PASS
- 시크릿 창 링크 검사
- 다른 컴퓨터에서 DOCX·ZIP 열기
- 제출문 작성

## 13. 이번 재설계에서 폐기하거나 바꾼 것

- HTML과 문서에 문장을 따로 복사하는 방식 → `approved.json` 단일 원본
- 2025년 근무를 두 번째 핵심 장면으로 두는 구조 → CLOV 회복 장면으로 통일
- 로그인 필요한 CLOV 서비스 링크 → 공개 저장소 링크만 사용
- 실제 문서가 없는데 눌리는 자기 링크 → 파일 생성 전 비활성 상태
- 실제 원본을 장치 ZIP에 포함할 가능성 → 합성 입력과 공개 집계만 포함
- GitHub Pages를 마지막에 수동 확인만 하는 방식 → Gate 2에서 먼저 공개하고 Gate 5에서 재검사
- 자리표시자를 눈으로 찾는 방식 → 릴리스 검사기가 자동 실패

이 설계의 최우선 기준은 “한 번 만든 소개 페이지”가 아니라, 새 기록이 생겨도 사실과 숫자를
잃지 않고 다시 만들 수 있는 제출물이다.
